## CI (GitHub Actions)

Built on its own `feature/ci` branch and merged into `develop` before the Phase 1 PR, so that PR is the first one CI checks. One workflow, `.github/workflows/ci.yml`, runs on every pull request into `develop` or `main` and on pushes to both.

- **Steps:** `npm ci` (clean install from `package-lock.json`, install scripts off via `.npmrc`), `npm audit signatures` (checks every package was signed by the npm registry), `npm run typecheck`, `npm test`, `npm run build`, then `npx vsce package`, which catches manifest mistakes such as `@types/vscode` being newer than `engines.vscode`. The `.vsix` is uploaded as the `0xword-vsix` artifact (kept 14 days) so the owner can playtest each PR with "Install from VSIX…". The workflow can also be run by hand from the Actions tab.
- **Runner:** `ubuntu-latest` with Node 24 (`actions/setup-node`, `cache: npm`).
- **Locked down:** only GitHub's own actions (`actions/checkout`, `actions/setup-node`, `actions/upload-artifact`), each pinned to a full commit SHA rather than a tag. `permissions: contents: read`. No secrets in the workflow.
- **Secret scanning:** the repo is private for now, so rely on the local gitleaks pre-commit hook plus vsce's own secret check when packaging. Before publishing, make the repo public (SECURITY.md's private vulnerability reporting needs that) and turn on GitHub secret scanning with push protection, which is free for public repos. A gitleaks step in CI would add a new tool and needs the owner's approval first.
- **Dependabot (security updates only):** `.github/dependabot.yml` watches npm and the pinned GitHub Actions. When a known vulnerability affects one, Dependabot opens a PR into `develop` that bumps it to the lowest fixed version. Routine version-bump PRs are off (`open-pull-requests-limit: 0`). Dependabot never merges: CI runs on its PR and the owner reviews and merges. Alerts are under Security → Dependabot. `develop` is the default branch, so these PRs target it.
- **Releases (Phases 5 and 6):** a separate `release.yml` runs only when the owner pushes a `v*` tag on `main`. It checks the tag against `package.json`, runs all of `ci.yml` through `workflow_call`, waits for the owner's approval, then publishes the `.vsix` CI built and tested, and creates a GitHub Release. Merges never publish. See [release-pipeline.md](release-pipeline.md).
- **Branch protection** on `develop` and `main`: changes go in only through a PR, the CI check *Typecheck, test, build and package* must pass, and one approving review is required. Nobody pushes directly to either branch, agents included. GitHub doesn't let the owner approve their own PRs (including those agents open under the owner's account), so the owner reviews them and merges with the admin bypass. Dependabot's PRs can be approved normally.

## Agent workflow

Claude Code agents in `.claude/agents/` and skills in `.claude/skills/` do the building; the owner approves stories, playtests, and merges.

- **Agents:** `developer` builds stories and fixes bugs with unit tests, then pushes its branch. `reviewer` (read-only) checks each branch against the acceptance criteria and the security rules. `qa-engineer` tests each PR and files bugs as issues with a failing test.
- **`/plan-phase <n>`:** proposes the phase's stories with acceptance criteria. After the owner approves, it creates a phase issue with one story sub-issue per slice. Safe to re-run; it never duplicates a story.
- **`/story #<issue>`:** takes one story or bug to ready-to-merge: build → review → PR into `develop` → CI → QA → fix `blocks-pr` bugs → hand over. Progress is tracked in a status comment on the issue, so it resumes instead of starting twice.
- **`/release <patch|minor|major>`:** bumps the version, updates `CHANGELOG.md`, and opens the release PR into `main`. The owner tags the merge, which starts `release.yml`, and approves the publish (see [release-pipeline.md](release-pipeline.md)).
- **Labels:** `phase` (phase issue), `phase-<n>`, `story`, `bug`, `in-progress`, `in-review`, `blocks-pr` (bug blocking an open PR), `agent-found` (filed by `qa-engineer`).
- **Owner's checkpoints:** approve the stories, merge each PR after playtesting the CI-built `.vsix`, tag releases, and approve each publish.

## Phase 1: Game engine

`src/game/` contains pure TypeScript with no VS Code imports.

- **Hex conversion:** `wordToHex("BYTE")` returns `"42595445"`, and `hexToWord` converts back, rejecting anything that isn't a capital letter (`41`–`5A`).
- **Scoring:** `score(guessHex, answerHex)` gives a right spot / wrong spot / not in word result for each of the 8 digits, handling repeated digits correctly. Port the logic from the old `wordle/web/wordle.js`.
- **Guess checking:** exactly 8 hex digits, every pair a letter, and the decoded word must be in the word list.
- **Answer pick:** a random word from the word list at the start of each round.
- **The round:** 6 rows, a decode step with one word try once a row is fully right or row 6 is scored, the hints letters (a byte shows its letter once both of its digits are in the right spot), and the result (solved, rows used, answer tries, hints used). **Changed in #30:** answer tries are counted apart from rows again. **Changed in #38:** "hints used" is a count, not a flag. **Changed in #46:** answer tries are always 1, and the round reaches the decode step on a fully right row as well as after row 6.
- **Round rules (agreed):**
  1. The player guesses hex rows, and can try the word only at the decode step: once a scored row has all 8 tiles in the right spot, at any row, or once row 6 is scored. Then the hex locks and the player gets one try: the right word solves the round, and a wrong listed word fails it, even with the grid solved. **Changed in Phase 3:** #20 made one try compulsory after every row (a misreading); #30 made tries optional and unlimited once a row was scored; **the owner's decision on #46** replaces that with the decode step. There is still no skip action.
  2. An all-right hex row doesn't win on its own; it opens the decode step, where the player still types the word.
  3. A malformed or unlisted answer is rejected without using up the try, and so is a hex row already scored (#30, #34).
  4. A byte's hint letter shows once both of its tiles have been in the right spot **in the same row**; otherwise it shows `?`. **Changed by #50 (owner's decision, 2026-10-25):** before #50 the letter showed once each tile had been right in any row, even different ones.
  5. Once hints are enabled the result records them as used. **Changed in Phase 3 (owner's decision on #38):** the result counts them: one hint per stretch of the round in which Hints was turned on, where a stretch is the time before each scored row. A scored row turns Hints off. **Changed in #46:** Hints locks with the hex at the decode step, so nothing is counted after the last row, and a round counts at most `rowsUsed` hints.
- **Tests** with `node --test`:
  - scoring cases with repeated digits (e.g. answer BYTE `42595445` against guess TEAM `5445414D` gives wrong spot ×4, not in word ×2, right spot, not in word)
  - the forced final answer
  - hint letters
  - rejection of invalid guesses

## Phase 2: Extension shell

- **`package.json` contributions:** an activity-bar view container with the 0xWORD icon, a webview view, the command `0xword.newRound`, and `capabilities.untrustedWorkspaces.supported: true`.
- **`src/extension.ts`:**
  - registers a `WebviewViewProvider`
  - sets `enableScripts: true` and limits `localResourceRoots` to `media/`
  - generates a fresh nonce on every load for the strict CSP: `default-src 'none'; script-src 'nonce-…'; style-src ${cspSource}; font-src ${cspSource}; img-src ${cspSource}`
- **Message protocol** (`src/protocol.ts`): typed messages between the game and the extension host. The host accepts only an allowlist (`ready`, `roundFinished`; `setTheme` was added in Phase 3, #26) and validates every field against the engine's limits. Host → webview messages are `init` (carrying the stats), sent in reply to `ready`, and `newRound`; the webview checks them just as strictly. Both sides use the same untrusted-data readers in `src/game/plain.ts`.
- **New Round command** (`0xword.newRound`, "0xWORD: New Round"): opens the panel and posts `newRound` (host → webview, no fields). If the webview isn't listening yet (closed, hidden or loading), each run is counted (`src/newRoundRequests.ts`) and sent after `ready` → `init`, so every run starts exactly one new round. The round lives in the webview: a `Session` (`src/game/session.ts`) starts a fresh engine `Round` for every `newRound`, and for `init` only if no round was restored. The placeholder shows "Round N".
- **Round persistence (owner's decision on PR #16):** the webview saves the session (version, round number and the whole round, answer included) with `vscode.setState` after every change, and restores it with `vscode.getState()` before it sends `ready`. So hiding, collapsing or reloading the panel keeps the round. No `retainContextWhenHidden` and no host-side store: VS Code keeps a webview view's state while it's hidden and across restarts. Saved state is untrusted: `Session.fromState` / `Round.fromState` check it strictly (exact keys, known version, the answer in the word list) and replay every saved guess and answer through the engine. Anything that doesn't match is dropped and a fresh session starts. The answer stays in that webview-only storage; it's never put in a message to the host, and goes in the DOM only on the result card once the round is over (#24).
- **Stats** (`src/stats.ts`) saved in `context.globalState` under the one key `0xword.stats.v1`: played, solved, the solved-rows total and the hints-used count (rounds with at least one hint; since #38 a round reports how many it used, and stats still count the rounds). Average rows and the hints-used rate are derived (null before there's anything to divide by). Each valid `roundFinished` adds to them; corrupted stored stats reset to zeros, and a failed write never throws. `init` carries the counts and derived values for Phase 3 to show.
- **Check:** pressing F5 opens the panel.

## Phase 3: Game UI

Rules carried over from Phase 2:

- **Every game action goes through `changed()`** (owner's decision). New round, guess, answer and turning hints on must each end with the `changed()` helper in `media/main.ts`, which saves the session with `setState` and redraws. A move that skips it is lost when the panel is hidden. Route all actions through one function, with a test that every action saves.
- **Send `roundFinished` once, when a round ends** (solved or failed). Never send it when New round replaces an unfinished round, or the stats would count rounds nobody finished.
- **Show the stats** that `init` carries (played, solved, average rows, hints-used rate). **Deferred to a later phase (owner's decision on #24):** the host keeps counting them, but Phase 3 doesn't show them.
- **Manual check:** hide the panel and run New Round straight away. The round must still start; VS Code's behaviour for a message sent to a hidden webview couldn't be tested automatically.

- **No skipping (owner's decision), replaced by optional decoding (#30):** #20 removed `skipAnswer()` and made one word attempt compulsory after every row, and PR #28 dropped `answerTries` because it always equalled rows used. That rule came from a misreading. Since #30 the player guesses hex rows freely and decodes when ready; there is still no skip action.

- **Optional decoding (#30):** **superseded by the decode lock (#46)**: word attempts are no longer optional or unlimited, the Tried list is gone, `answerTries` is always 1, and a word can't be a repeat. The hex-row repeat rule and the scored-row announcements below still hold. A scored row before row 6 no longer blocks the next `submitGuess`: the `answer` phase is gone, so the round is `guess` until row 6 and then `final`. `Round.canDecode` is true once a row is scored and until the round is over: the decode box and its button are enabled then (owner's decision: not before row 1). Word tries are unlimited (owner's decision); a wrong listed word joins the Tried list and uses no row, and a malformed or unlisted word is rejected with a plain-text reason and isn't counted. **Repeats are rejected (owner's decision):** a word already tried in the round (compared in any letter case) gets "You've already tried BEAT", isn't counted and leaves the phase alone, even as the forced final answer; a hex guess already scored gets "You've already tried 42 41 52 4E" (the guess in uppercase byte pairs, as the grid groups them; owner's wording from the PR #42 playtest), keeps its digits and uses no row (the engine's `"repeat"` errors). The keypad, DEL and ENTER stay enabled until row 6, and nothing moves focus to the decode box before the hex locks; after an accepted wrong word, focus goes back to the page, where physical keys drive the hex grid, while a rejected word keeps its text and focus in the box. Wrong-word feedback ("BEAT isn't the word") is for screen readers only. A scored row shows no message: the tile colours show it, and its marks ("Row 2: 4 Right spot, …") are read out from a visually hidden live region (owner's decision). The "1 try per row" note is gone. `answerTries` is back in the result, `roundFinished` and the result card's line, which reads "N of 6 rows · M answer tries · no hints" as page 4 draws it ("1 answer try" in the singular). The host accepts `answerTries` from 1 (every round ends with a word attempt: the right word, or the wrong final answer) up to the word list's size for a solved round (every other word wrong, then the answer) or one less for a failed one (every wrong word), since each listed word counts once. The host doesn't load the list, so `WORD_LIST_SIZE` in `src/game/words.ts` holds the count, and a test keeps it equal to `words.txt`. Saved state is now version 6: the round's `answers` are recorded apart from its rows (any number, including none, but no repeats) and replayed strictly on restore, so a repeated row or word is rejected; version-5 state is dropped, so the panel starts fresh.

- **Grid and decode (#21):** the game screen's logic lives in a pure UI controller, `src/ui/game.ts` (no DOM, no `vscode`): the actions (`init`, `newRound`, `digit`, `delete`, `enter`, `decode`), the messages, the key states and a render model. Its `dispatch` is the one action function, and it always ends with `changed()`; a unit test checks every action type saves. `media/main.ts` is a thin DOM layer that draws the model with `createElement` and `textContent`. All styling is in `media/styles.css`, loaded with a `<link>` under the unchanged CSP. The dark palette and its contrast check are in `src/ui/palette.ts`. Saved state is now version 3: it adds the half-typed hex row (`draft`: up to 8 uppercase hex digits, empty whenever a word attempt is due or the round is over). Version-2 state is dropped, so the panel starts fresh. On purpose, only the hex draft is saved: a word half-typed in the decode box is lost when the panel is hidden, and the box is simply empty again.

- **Final answer (#22):** once all 6 rows are scored and the round isn't over, the view's `hexLocked` is set: the status line shows a lock icon and "Hex locked · all 6 rows used", the grid and keypad are dimmed (keys stay `disabled`), and the decode panel becomes page 3's orange "Final answer" card. It's keyed off the rows, not the phase name, so it doesn't depend on the per-row decode rule. **Changed in #46:** `hexLocked` is the decode step (the `decode` phase), reached by a fully right row too; the lock icon and dimmed grid show only after row 6 without one (`outOfRows`). `roundFinished` is sent exactly once per finished round: `dispatch` asks `Session.takeResult()`, which hands out the result once and sets the session's `reported` flag, and passes it to `changed()`, which saves first and then posts. New Round on an unfinished round sends nothing. Saved state is now version 4: it adds `reported` (a boolean, true only for a finished round), so a finished round restored after a hide or reload is never sent again. Version-3 state is dropped.

- **Hints (#23):** the Hints button on the right of the status line is an on/off toggle (`aria-pressed`), off at the start of every round. It can be pressed any number of times while a round is in progress, including at the final answer, and is hidden once the round is over. While it's on, a strip between the grid and the legend shows one dashed cell per byte with its letter or a muted `?` (page 2), read out as one line ("Hints: B, unknown, T, E"). Hints are unlimited: there is no counter anywhere. The engine keeps two flags: the toggle (`hintsShown`, `enableHints()` / `disableHints()`) and the one-way `hintsUsed`, which is set the first time hints are turned on and goes into the result and `roundFinished`. Each toggle is a `toggleHints` action through `dispatch` → `changed()`. Saved state is now version 5: the round adds `hintsShown` (a boolean, true only if `hintsUsed` is). Version-4 state is dropped. **Replaced by the hint count (#38)**: Hints now switches off after each scored row, and the one-way flag is a count. **Changed in #46:** Hints can no longer be pressed at the final answer: it locks at the decode step (off, `disabled`, with a lock icon) for the rest of the round.

- **Result card (#24):** once a round is over, the view's `result` holds page 4's card, which replaces the legend, the decode panel and the keypad: an outcome line ("Congrats! You cracked it" or "Unlucky!", the owner's wording; not on page 4) above the heading, "Decoded: BYTE" for a solved round or "The word was BYTE" for a failed one, the line "N of 6 rows · M answer tries · no hints" (or "· hints used"; the answer-tries count came back in #30; **since #38** "N of 6 rows attempted · M hints used"), one tile per byte (`42`, a down arrow, `B`), a **New round** button and, under the card, "Your agent is still working. Next round is ready when you are." The status line reads "4-letter word · solved" or "4-letter word · not solved" (**since #46** "· out of rows" after row 6, or "· not decoded" after a wrong word on a solved grid). `result` is the only part of the view that holds the answer, and it's null while the round is in progress, so the answer goes in the DOM only once the round is over. New round is the existing `newRound` action through `dispatch` → `changed()`, so it posts no `roundFinished`; a finished round restored after a hide or reload brings the card back, and `reported` stops it being posted again. Built in the dark palette from existing dark tokens; the light theme comes with the theme story. No saved-state change.

- **How to play (#25):** the `?` button on the right of the header opens page 5's How to play in place of the game, from any screen; its back arrow or Escape closes it, with focus back on `?`. The rule wording, the cheatsheet line and the 26 cards (`A 41` to `Z 5A`, from the engine's `letterToHex`, which `wordToHex` also uses) are data in `src/ui/howToPlay.ts`, so a later rule change touches only that file. Opening and closing are `openHowToPlay` / `closeHowToPlay` actions through `dispatch` → `changed()`; while it's open the controller ignores every game move (`APPLIES_WHILE_HOW_TO_PLAY_OPEN`, which every action type must be listed in) and the keydown handler passes no key on but Escape, so the game comes back unchanged. Its open state isn't saved: a reload shows the game. No saved-state change. On close, focus goes back to `?` only if How to play was opened from the keyboard; opened with the mouse, focus goes back to the page (or the decode box, if the final answer is due; before #30, whenever a word attempt was due), so a physical Enter or Space can't reopen it. A standing message isn't read out again on close: the view's `noticeId` changes only when an action sets a new message. **Deliberate:** the New Round command keeps How to play open and starts the round behind it.

- **Theme (#26):** the panel follows VS Code's theme by default: `vscode-dark` and `vscode-high-contrast` get the dark palette, `vscode-light` and `vscode-high-contrast-light` the light one from page 4. A sun/moon button next to `?` cycles System → Light → Dark → System; it shows a sun while the dark palette shows and a moon while the light one does, and its accessible name says what the next press does. Both palettes are CSS custom properties in `media/styles.css` (dark in `:root`, light in one rule on `<body>`), matching `DARK_PALETTE` and `LIGHT_PALETTE` in `src/ui/palette.ts`; the webview only sets `data-ox-theme` on `<body>` for a forced choice, so "System" follows a VS Code theme change live with no script. The light values for screens drawn only in dark are derived from page 4's values and listed in [docs/design/README.md](design/README.md#light-values-derived-for-screens-drawn-only-in-dark-26). The webview sends `setTheme {theme}` (`"system"`, `"light"` or `"dark"`; anything else, an extra field or a wrong type is ignored), and the host keeps it in `globalState` under `0xword.theme.v1` (`src/theme.ts`, like the stats store; a corrupt value reads as "system"). `init` carries it, and the host also puts a forced choice on `<body>` in the HTML so the panel doesn't flash the other palette before `init`. VS Code loads the same HTML again when a hidden view is shown, so the host rebuilds it whenever the view is hidden (`viewVisibilityChanged`), never while it's shown. Changing the theme isn't a game action: it doesn't go through `changed()` and isn't in the saved round. No saved-state change. The contrast test covers every text pair in both palettes; page 3's dimmed dark keys (3.42, 2.45 and 3.80:1, `disabled`) are listed for the owner rather than changed.

- **Fonts (#27):** DM Sans and JetBrains Mono are bundled in `media/fonts/` with their OFL licences, downloaded once from `github.com/google/fonts` (`ofl/dmsans`, `ofl/jetbrainsmono`) at a pinned commit and committed unchanged apart from the file names. Only the upright variable files ship: DM Sans covers weights 100 to 1000 (the title's `WORD` is 1000) and JetBrains Mono 100 to 800; no italics are used. `media/fonts/README.md` records each file's source URL, commit and SHA-256, and a test checks every checksum; `.gitattributes` keeps the files byte for byte so the checksums hold on every checkout. `media/styles.css` loads them with `@font-face` by relative URL under the existing `font-src ${cspSource}`, with `font-display: swap`; `--ox-sans` and `--ox-mono` name the bundled family first and keep the system fallbacks after it, so the panel still renders if a font fails to load. No build step fetches anything.

- **No repeats (#34):** built. **Changed in #46:** with one try per round a word can't be repeated, so the word half of the rule is gone (rule 5 now covers hex guesses only, and a word rejection is `format` or `notWord`); the saved rejection still restores a rejected word at the decode step. The repeat rule itself shipped in #30 (PR #42), with its wording; this story added what was left. How to play has a new rule 5, "You can't repeat a hex guess or an English word in the same round. A repeat doesn't use up a row or a try.", so the final-answer rule is now 6 and Hints 7. The engine gained `Round.rowError` and `Round.answerError`, which say why a row or word would be rejected without changing anything (the invalid checks first, then the repeat check); `submitGuess` and `submitAnswer` use them. **Messages survive a hide and show (owner's decision):** the session saves the last rejected move as data, `rejection` (`{kind: "row", error, hex}` or `{kind: "word", error, word}`, with `word` "" for a format error), never as text, and the controller rebuilds the message from it. Every action sets it through `dispatch` → `changed()`, so it's saved with the move, and any other change to the session clears it. On restore it's untrusted. `readRejection` checks its form: exactly those keys, a known error code, a row's `hex` equal to the saved draft while the round waits for a hex row, and a word that's four letters A–Z (or "" exactly for a format error) while the round can take one; a malformed rejection drops the saved state. `stillApplies` then asks the round to work the error out again for that input: if it no longer matches (a later release added the rejected word to the list, say), the round is kept with no message, so adding words never loses a round in progress. A restored message is drawn in the first render, as page content, and `init` keeps it without counting a new notice, so it isn't read out again as new; the same error entered again is. Screen-reader-only announcements and the decode box's text aren't saved. Saved state is now version 7; version-6 state, which can't hold anything version 7 rejects, is still restored with no message, and older state is dropped.

- **Placeholder ellipsis (#33):** built, CSS only. The decode box's placeholder ends in an ellipsis when it doesn't fit, both "Type the English word" and the final answer's "Decode the bytes above", and shows in full when it fits. Chromium shows no ellipsis while the box has focus, so then a placeholder that doesn't fit is hidden instead (owner's decision): the decode row is a size container, and `@container` rules hide "Type the English word" below a 257px row and "Decode the bytes above" below 271px (panels of about 309px and 323px), widths measured with the bundled fonts. A test ties those widths to the `DECODE_PANEL` and `FINAL_PANEL` strings, so rewording one fails until it's measured again. Because the cut-offs depend on text width, `body` now sets `font-weight: 400` too, so VS Code's default webview styles change no size. **Equal tiles and a fixed keypad (owner's decisions on PR #45, 2026-10-23):** every grid row and the hint strip use the same columns, `repeat(4, minmax(var(--ox-pair-min), 1fr))`, and each pair splits into two equal columns, so an empty tile is exactly the size of a typed, scored or dimmed one at every width, on the result screen too. All tiles grow together and stop at 29.2px (`--ox-tile-min`: one 18px digit line and its border); narrower than that, the grid overflows and the panel scrolls sideways. Keypad keys never grow: each column is `minmax(--ox-key-min-width, --ox-key-width)`, at most 89.5px, their width in a 400px panel (so DEL and ENTER are 185px), and at least 87px, their width when VS Code's 10px scrollbar narrows that column to 366px (owner's decision). With `margin-inline: auto` the keypad is centred in wider panels, fits a 366px column with its right edge on the grid's, and below that overflows to the right; keys stay 44px tall. Before, the game column capped at 400px, so keys grew to 95.5px in panels from about 424px wide; now they stay 89.5px. **Known limits:** below about 366px, with the page scrolled fully right, the right-hand keys' focus ring can be cut at the scroll edge; from about 424px wide the 376px keypad is narrower than the 400px grid and centred, so their edges no longer line up. **Dropped:** the panel-height criteria (tiles limited by the panel's height) and the tighter message line. - **Hint count (#38):** built; replaces #23's one-way "hints used" flag (owner's decisions, 2026-10-23). **Changed in #46:** Hints locks with the hex at the decode step, so there's no stretch after the last row and no wrong word to switch it off: a round counts 0 to `rowsUsed` hints, `MAX_HINTS` is 6, and the host accepts 0 to `rowsUsed`. Hints is still an on/off toggle, off at the start of each round, unlimited, and pressed any number of times, but **ENTER on a scored row turns it off** and hides the strip, and so does an accepted wrong word (owner's decision on #38, after the first build), so the player turns it on again when they want help. A rejected row (invalid, not a listed word, or a repeat) and a rejected word (malformed, not listed, or a repeat) leave it on; a right word ends the round anyway. The engine (`Round`) counts hints: the round is split into stretches by its scored rows, one before each row and one after the last row until the round ends (the forced final answer, or a decode that solves it), and a stretch counts once if Hints was turned on at any point in it, however often it was pressed and even if it was off again at ENTER. A rejected row doesn't end a stretch, and nor does a word attempt: Hints turned back on after a wrong word, before the next row, isn't counted again. So a round counts 0 to `rowsUsed + 1` hints, at most `MAX_HINTS` = 7. The count only grows and is never shown while the round is in progress. `Round.hintsUsed`, the result, `roundFinished` and `takeResult` carry it as a number; the host accepts a whole number from 0 to `rowsUsed + 1` (so never above 7) and rejects the old boolean, and a test checks every solved × rowsUsed × answerTries × hintsUsed combination against real rounds. Stats keep `hintsUsedCount` as the number of rounds with at least one hint, so stored stats and the hints-used rate keep their meaning; showing stats is still deferred. The result card's line is now "N of 6 rows attempted · M hints used" ("1 hint used", "0 hints used"): answer tries stay in the result, `roundFinished` and the stats, but aren't shown. How to play's rule 7 is now the owner's "Stuck? Turn on **Hints** to see the letters you've fully decoded. It switches off after each hex row, and every use is counted in your result." The switch-off happens inside `submitGuess` and `submitAnswer`, so it goes through `enter` or `decode` → `dispatch` → `changed()` with the row or word. Saved state is now version 8: the round's `hintsUsed` is the count, next to `hintsShown` and a new `rowHinted` (Hints was turned on in the current stretch, so it's already counted). On restore all three are checked strictly: `hintsUsed` a whole number up to 7, `hintsShown` only if `rowHinted`, and the hints from scored rows (`hintsUsed`, less one if `rowHinted`) between 0 and the rows; the replay then turns Hints on through the public methods to rebuild exactly that state. Version-6 and version-7 state is dropped, so the panel starts fresh: their one-way flag can't say how many hints were used.
